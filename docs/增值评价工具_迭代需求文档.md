# 增值评价工具迭代需求文档

## 1. 背景与目标

现有系统已经跑通了"一个量规 + 一个数据包 → 双评 + 仲裁 → 评分与反馈"的单件评价链路，且具备了**"配置驱动、平台无关"**的通用性特点。

本次迭代要解决的不是单件评价的质量问题，而是新增一个维度：**同一个学生在不同时间点被反复测量，如何计算和呈现其能力的增益（增值）**。

系统的定位从"评价一件作品"扩展为"追踪一个学生"——学生成为系统的第一级实体，课程/项目只是学生某一次测量所在的场景，进一步要求通用性。

## 2. 协作路线与接口边界

本次迭代按两条并行路线推进，两条线通过接口对齐，互不阻塞：

| 路线 | 负责人 | 职责范围 |
|---|---|---|
| 打分引擎 | 吴海涛 | 模态解析能力、取证 + 评分流水线、仲裁逻辑、增值计算模型、反馈生成 |
| Web 平台/前端 | 李领康 | 任务发起、学生邀请与提交、学生档案与时间轴、结果可视化（雷达图/证据链展示）、教师审核工作台 |

**需要尽快对齐的接口契约**：

- 打分引擎的输入/输出数据结构（量规文件格式、数据包格式、单轮评分结果的字段定义）
- 学生档案与任务的唯一标识规则（学生 ID、任务 ID、轮次序号、时间戳如何贯穿两端）
- 增值计算由谁触发、算在哪一端——建议是前端聚合多轮引擎结果后调用引擎的增值子服务

## 3. 核心数据模型

- **学生**：第一级实体，脱离具体课程/项目独立存在，拥有档案与时间轴
- **测量任务**：教师发起，邀请学生，学生提交；任务按发起教师和提交时间戳排序
- **数据包**：一次提交对应的原始材料，格式不限（对话记录/项目作品/需求文档/设计文档/代码/毕业论文+代码等），系统不做内容层面的区分，只要求外层封装符合规定格式
- **量规**：单独一个文件，定义评价维度与等级描述

## 4. 数据接入层

- 多源文件解析（PDF/Word/Excel/PPT/JSON/Markdown 等）通过成熟的第三方商用 API 完成，不自研解析能力【吴海涛负责调研可靠云服务，按调用计费】
- 教师可一次性上传含多名学生数据的压缩包，用于增值评价场景下的批量导入与批量评价
- 保持"轻量"原则：引擎侧只关心"量规 + 数据包"这一最小输入单元，不关心数据包内部来源；任务管理、学生邀请等业务流程留在前端侧

## 5. 评价流水线 v2（取证 + 评分合并）

相较于现有的"共享证据抽取 → Rater1/Rater2 背靠背打分"架构，本轮迭代调整为：

- **Rater 1**：独立完成取证 1 + 评分 1（不与 Rater 2 共享证据集）
- **Rater 2**：独立完成取证 2 + 评分 2（不与 Rater 1 共享证据集）
- **Rater 3（仲裁）**：先看 Rater1、Rater2 各自的取证 + 评分链路，并按需结合最初的量规与数据包给出最终判断

这个改动让两位评分者从"共享同一份证据、各自打分"变成"各自独立完成证据到结论的完整链路"，理论上能进一步降低共享证据带来的相关性偏差，但也意味着计算成本翻倍（每轮两次完整的取证 + 评分）。

## 6. 增值计算模型

- 增值的最小前提：同一学生至少有两轮测量结果落在同一评价维度上，否则无法比较
- 未解决的核心难点：不同轮次使用的量规可能不同（难度不一），无法直接归一化到同一把尺子上比较分数
- 暂定方向（供讨论，非结论）：先只支持"同一量规、跨轮次"场景下的增值计算，"跨量规折算"作为二期问题

## 7. 反馈与输出

- 每轮评价结束后给出反馈，包含雷达图展示与建议改进反馈
- 反馈以文字为主、图形化为辅，服务于学生理解与改进
